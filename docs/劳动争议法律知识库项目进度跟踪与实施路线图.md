# Legal Registry V2 项目进度跟踪清单

## 1. 项目目标

建立以 Canonical Registry V2 为权威结构化数据层、
以 Qdrant 为派生向量检索层的法律 RAG 数据架构。

通过统一的法律身份、法律版本、权威来源、法条正文及来源追溯关系，
保证法律数据可识别、可验证、可重建、可追溯。

本文件是项目长期进度跟踪基准。

每个阶段开始前，应先阅读本文件，确认整体路线、已完成阶段、
当前阶段、阶段目标和进入条件。

每个阶段结束后，应及时更新本文件，记录实际交付物、
验证结果、Git Commit 和下一阶段安排。

## 2. 项目架构边界

项目采用以下分层：

1. 权威法律来源层：保存官方原始法律文件及来源信息。
2. Canonical Registry 层：管理法律、法律版本、来源、法条及身份关系。
3. Qdrant 向量检索层：从正式 Registry 派生构建向量和 Payload。
4. 检索与决策层：使用检索结果提供法律依据，并交由法律规则和决策系统处理。

核心原则：

- Canonical Registry 是法律结构化数据及身份关系的权威来源。
- Qdrant 是派生检索层，不反向决定法律身份、版本或权威正文。
- 新 Qdrant 数据必须从正式 Registry 重新构建。
- 不使用旧 Qdrant Points 作为新 Collection 的迁移数据来源。
- LegalArticle 与 Qdrant Point 不预设一对一关系。
- 旧 Collection 在新 Collection 完整验收前不得删除。
- 删除旧 Collection 前必须重新核对目标并取得用户明确确认。
- Registry JSON 的事务保护机制必须保留。

### 二、阶段 A：Identity 身份层

### 目标

建立 Canonical Registry V2 的确定性身份生成协议，为 Law、LawVersion、Source 和 ArticleSource 提供稳定身份。

### 修改范围

| 文件 | 操作 |
|---|---|
| `src/legal_identity.py` | 扩展确定性身份生成函数 |
| `tests/test_legal_identity.py` | 扩展 pytest 测试 |

本阶段不修改 Models、Store、Builder、Qdrant 和正式 Registry JSON。

### Namespace

使用已经定稿的四个 Namespace：

- LAW_NAMESPACE：`0e6d1b4a-72c8-5f31-9a40-2b7e6d8c1f53`
- VERSION_NAMESPACE：`1f7c2a90-8b43-5d61-ae20-3c9f7b5d1a64`
- SOURCE_NAMESPACE：`2a8e3c51-9d74-5f20-b136-4e0a8c6d2f75`
- ARTICLE_SOURCE_NAMESPACE：`3b9f4d62-ae85-5c31-c247-5f1b9d7e3a86`

现有 ARTICLE_NAMESPACE 必须原样保留。

### 身份生成函数

统一提供：

- `build_law_id(jurisdiction, canonical_law_name)`
- `build_version_id(law_id, version_key)`
- `build_source_id(official_source_url, source_hash)`
- `build_article_id(version_id, article_number)`
- `build_article_source_id(article_id, source_id)`

### 规范化和序列化

新身份使用规范 JSON：

- `ensure_ascii=False`
- `sort_keys=True`
- `separators=(",", ":")`
- UTF-8 编码
- UUID5 生成身份

Law 名称使用 NFKC、去除首尾空白、合并连续空白。

Source URL 规范化遵循已定稿规则：

- 仅允许 HTTP/HTTPS。
- Scheme 和 hostname 转为小写。
- 移除默认端口。
- 移除 Fragment。
- 保留实际路径。
- 保留查询参数及其顺序。
- 拒绝 URL 用户名和密码。
- 不使用文件名或本地路径代替官方 URL。

Source Hash 使用原始文件 SHA256。

### Article ID 兼容要求

现有 `build_article_id()` 的：

- Namespace；
- 身份输入；
- 条号规范化；
- UUID5 生成方式；

全部保持不变。

不得为了统一接口而改变现有 Article ID。

7. ArticleSource 身份稳定性。
8. 字典键顺序变化不影响身份。
9. 固定输入的身份回归测试。

### 四、阶段 C：Registry Builder 与初始化流程

### 目标

建立统一的 Registry 构建入口，消除旧 Preview 脚本中的重复解析和 Qdrant 正文依赖。

### 新增模块

`src/legal_registry_builder.py`

### Builder 职责

1. 读取法律来源配置。
2. 定位权威原始 DOCX。
3. 校验原始文件 SHA256。
4. 调用 `legal_document_parser.py`。
5. 获取 Parser 返回的 ParsedDocument 和 ParsedArticle。
