# 劳动争议法律知识库项目开发与实施管理规范

**文档级别：项目级管理规范**
**适用范围：劳动争议法律知识库整个项目**
**维护位置：项目工程 `docs` 目录**
**管理原则：整体规划、现状审计、文档先行、分阶段实施、逐步骤交付、版本可追溯**

---

# 一、项目实施总体原则

## 1.1 现有功能优化升级原则

1. 项目开发以现有项目功能为基础，优先采用优化、升级和扩展的方式实现新需求。
2. 不得在没有充分技术理由的情况下，随意推翻现有功能或重新设计已经成熟的模块。
3. 实施新功能时，必须评估对现有功能、模块职责、数据结构、公共接口和业务流程的影响。
4. 如确实需要调整现有架构或重构已有功能，必须先完成现状审计、影响分析和设计方案确认。
5. 不得为了实现新功能而无故牺牲已有功能。

## 1.2 项目功能整体规划原则

1. 项目采用整体规划、分功能实施的方式进行开发。
2. 在实施具体功能之前，必须明确整个项目的功能规划。
3. 所有项目功能统一维护在唯一的项目功能清单文档中。
4. 每个功能必须明确其目标、功能边界、主要内容及与其他功能的依赖关系。
5. 新增功能必须先纳入项目整体规划，并更新项目功能清单。
6. 不得脱离项目整体规划，随意增加相互独立、缺乏整体设计的新功能。

## 1.3 项目架构整体设计原则

1. 项目采用整体架构设计、按功能进行详细设计和分阶段实施的方式。
2. 项目架构设计必须覆盖整体项目的功能划分、模块职责、模块依赖、数据结构及主要业务流程。
3. 项目架构统一维护在唯一的项目架构设计文档中。
4. 每个功能的详细设计必须符合项目整体架构。
5. 如果功能实施需要调整整体架构，必须先进行影响分析并更新项目架构设计文档。
6. 不得在未经整体架构评估的情况下，擅自改变公共数据结构、模块职责或系统接口。

## 1.4 统一测试原则

1. 项目所有自动化测试统一使用 pytest。
2. 新增功能必须同步设计和编写对应的 pytest 测试。
3. 修改已有功能时，必须执行对应的回归测试。
4. 涉及模块之间的接口、数据结构和业务流程时，必须进行相应的集成测试。
5. 测试失败时，必须分析和修复实际问题，不得通过随意修改测试预期结果掩盖代码问题。
6. 不得仅以新增测试通过作为整个项目验证通过的依据。

测试根据实际功能划分为：

- 单元测试。
- 模块测试。
- 集成测试。
- 数据结构及数据完整性测试。
- 回归测试。
- 端到端测试。

具体测试范围由各功能设计文档确定。

测试要求应根据步骤实际修改内容确定：

1. 涉及代码、测试逻辑、运行行为、配置或可执行接口契约的步骤，必须执行与修改范围对应的 pytest 测试及必要的回归测试。
2. 纯文档维护步骤，如果不影响代码、运行行为、配置或测试逻辑，不强制执行与本次修改无关的 pytest 测试。
3. 纯文档维护步骤必须执行适用的文档验证，包括内容、结构、引用、编码、差异及完整性检查。
4. 如果文档修改影响配置、接口契约或测试规范，必须根据实际影响补充相应的 pytest 验证。
5. 不得为了形式上满足测试流程而执行与当前步骤无关的测试，也不得以纯文档步骤为由跳过实际需要的测试。

## 1.5 项目实施路径

项目功能实施统一遵循以下路径：

1. 确定功能范围。
2. 检查项目文档及已有功能。
3. 对现有功能进行只读审计。
4. 根据审计结果进行整体设计和功能详细设计。
5. 确认实施方案及实施步骤。
6. 代码开发。
7. 执行适用的 pytest 测试验证；纯文档步骤执行相应的文档验证。
8. 实施后代码及架构审计。
9. 文档一致性检查。
10. 清理临时文件及不必要的备份文件。
11. 按照第 5.6 节规定的流程，先更新 Roadmap 中的实际实施及验证状态，并完成提交前审计。
12. 执行独立 GitHub commit/push，并核验远端版本。
13. 推送成功后补录 Commit SHA 和远端核验结果；补录后的 Roadmap 变更必须再次独立审计、commit/push。

其中，功能范围确定、现有功能审计和设计确认必须先于代码开发。

未经确认的设计方案不得直接进入代码实施。

## 1.6 Qdrant 数据管理原则

1. 项目不创建专门的 Qdrant 数据备份及恢复机制。
2. 不开发专门用于 Qdrant Point 或 Collection 备份恢复的程序。
3. 如果 Qdrant 数据出现问题，采用从权威原始法律文件重新解析、重新入库的方式恢复数据。
4. 必须保留权威法律原始文件及其必要的版本身份、来源信息和完整性校验信息。
5. 必须保证法律文件解析、数据构建及重新入库流程可以重复执行。
6. 必须具备重新入库后的数据完整性及检索验证能力。
7. 不得将取消 Qdrant 备份恢复机制理解为可以随意删除权威法律原始文件。
8. 涉及删除 Collection、清空数据或重建数据结构等破坏性操作时，必须先完成目标确认、影响分析和实施方案确认。

# 二、项目文档维护原则

## 2.1 文档统一管理原则

1. 项目正式文档统一维护在项目工程的 `docs` 目录下。
2. 项目文档必须纳入 GitHub 版本管理。
3. 文档修改必须与对应功能实施保持一致。
4. 不得在多个文档中重复维护同一项正式管理信息。
5. 每类项目级管理文档必须保持唯一正式版本。
6. 临时分析记录、调试记录不得替代正式项目文档。

## 2.2 项目功能清单文档

项目功能清单属于项目级文档，全项目只维护一份。

主要职责：

1. 记录整个项目需要实现的功能。
2. 记录各功能的目标及主要职责。
3. 记录功能之间的依赖关系。
4. 记录功能实施顺序及规划状态。
5. 新增、调整或取消功能时，及时更新该文档。

项目功能清单只负责整体功能规划，不承担具体功能设计和实施进度管理职责。

## 2.3 功能范围文档

功能范围文档属于功能级文档。

每个功能独立维护一份。

主要职责：

1. 明确当前功能的目标。
2. 明确功能实施范围。
3. 明确功能不包含的内容。
4. 明确当前功能与其他功能的依赖关系。
5. 明确当前功能的输入、输出及主要交付内容。
6. 记录当前功能实施前已经存在的相关功能。
7. 记录后续需要实施的功能及其范围概要。

每个功能开始实施前，必须先检查项目功能清单及相关功能范围文档，避免重复建设。

功能范围确定后，必须同步更新：

- 项目功能清单文档。
- 当前功能范围文档。
- 项目进度跟踪文档。

后续功能的范围概要只用于整体规划，不代表后续功能的详细实施方案已经确定。

## 2.4 项目架构设计文档

项目架构设计属于项目级文档，全项目只维护一份。

主要职责：

1. 描述整个项目的总体架构。
2. 描述项目功能划分。
3. 描述各功能的概要设计。
4. 描述模块职责及模块之间的依赖关系。
5. 描述主要数据结构及数据流转关系。
6. 描述关键业务流程和系统接口。
7. 记录项目整体架构的调整及其原因。

项目功能清单发生变化时，应同步评估项目架构设计是否需要更新。

如果新增功能影响现有架构，必须更新项目架构设计文档。

## 2.5 功能设计文档

功能设计文档属于功能级文档。

每个功能独立维护一份。

主要职责：

1. 描述当前功能的详细设计目标。
2. 描述当前功能的模块划分及职责。
3. 描述涉及的现有模块及其调整方案。
4. 描述数据结构、接口和业务流程。
5. 描述模块依赖及外部依赖。
6. 描述异常处理及边界条件。
7. 描述 pytest 测试设计。
8. 描述功能实施阶段和主要步骤。
9. 记录后续相关功能的设计概要。

功能设计前，必须检查项目架构设计文档及已有功能设计文档，避免重复设计和架构冲突。

功能详细设计确定后，必须同步更新：

- 当前功能设计文档。
- 项目架构设计文档。
- 项目进度跟踪文档。

功能设计不得未经评估就改变项目整体架构。

## 2.6 项目进度跟踪文档

项目进度跟踪文档属于项目级状态管理文档，全项目只维护一份。

该文档是整个项目实施状态的唯一正式记录来源。

正式文件路径：

`docs/劳动争议法律知识库项目进度跟踪与实施路线图.md`

整个项目只允许维护这一份正式进度跟踪文档。不得另外建立项目级进度表、第二份 Roadmap 或并行进度记录文件。

进度跟踪文档采用三个层级管理。

### 第一层：功能层级

按照项目功能清单记录所有功能。

每个功能至少记录：

- 功能名称。
- 功能目标。
- 功能状态。
- 功能实施阶段。
- 已完成阶段。
- 当前阶段。
- 后续计划。

### 第二层：阶段层级

每个功能根据功能设计划分为多个实施阶段。

每个阶段至少记录：

- 阶段名称。
- 阶段目标。
- 阶段实施范围。
- 阶段状态。
- 已完成步骤。
- 当前步骤。
- 遗留问题。
- 阶段完成条件。

### 第三层：步骤层级

每个阶段划分为多个具体实施步骤。

每个步骤至少记录：

- 步骤编号。
- 步骤名称。
- 实施目标。
- 实施状态。
- 实施内容。
- 修改文件。
- pytest 测试命令。
- pytest 测试结果。
- 审计结论。
- 清理结果。
- GitHub commit SHA。
- 遗留问题。
- 下一步工作。

步骤状态统一采用：

- 未开始。
- 进行中。
- 已完成。
- 阻塞。

进度跟踪必须以实际实施结果为依据，不得仅根据计划推断完成状态。

每个步骤开始前及完成后，必须及时更新该文档。

# 三、项目功能维护原则

## 3.1 项目功能整体规划

1. 项目按照功能划分实施。
2. 整个项目的功能必须提前进行整体规划。
3. 所有功能统一记录在唯一项目功能清单文档中。
4. 功能清单应记录功能目标、主要职责、实施顺序及依赖关系。
5. 后续发现需要新增的功能时，必须先进行整体评估。
6. 经确认需要新增的功能，必须更新项目功能清单及项目架构设计文档。

## 3.2 功能实施前的范围检查

每个功能开始实施前，必须：

1. 阅读项目功能清单。
2. 阅读当前功能及相关功能范围文档。
3. 检查已经实施的项目功能。
4. 检查已有功能的实际实现情况。
5. 确认当前功能是否与已有功能重复。
6. 明确当前功能与其他功能的依赖关系。
7. 确定当前功能的正式实施范围。

确定后，必须建立或更新当前功能独立的功能范围文档。

同时更新：

- 项目功能清单。
- 项目进度跟踪文档。

## 3.3 后续功能概要规划

确定当前功能范围时，必须结合项目整体功能规划。

在当前功能范围文档中记录后续至少两个相关功能的概要信息（如果项目剩余功能不足两个，则记录全部剩余功能）。

记录内容包括：

1. 后续功能名称。
2. 功能目标。
3. 主要解决的问题。
4. 预计功能范围。
5. 与当前功能的依赖关系。
6. 预计需要衔接的数据结构或接口。

后续功能仅进行概要规划，不提前确定未经审计的详细实现方案。

## 3.4 功能完成后的状态维护

当前功能完成后，必须：

1. 检查功能目标是否全部实现。
2. 检查功能范围是否全部交付。
3. 检查相关 pytest 测试是否通过。
4. 检查功能设计与实际实现是否一致。
5. 检查相关文档是否同步更新。
6. 检查所有阶段和步骤是否完成。
7. 将实际完成状态更新至项目进度跟踪文档。

不得仅根据代码修改完成就将功能标记为完成。

# 四、项目架构设计原则

## 4.1 项目整体架构设计

1. 项目采用按功能划分的整体架构设计方式。
2. 项目架构设计统一维护在唯一的项目架构设计文档中。
3. 项目架构设计应与项目功能清单保持一致。
4. 每项功能必须在项目架构中具有明确的职责和边界。
5. 项目架构必须明确各功能之间的依赖关系。
6. 项目功能清单发生变化时，必须同步评估架构设计。
7. 项目架构调整必须记录调整原因、影响范围和关联功能。

## 4.2 功能详细设计前的架构检查

每个功能进行详细设计前，必须：

1. 阅读项目架构设计文档。
2. 阅读当前功能及相关功能设计文档。
3. 检查已经实施功能的实际架构。
4. 检查已有模块职责及依赖关系。
5. 检查是否存在重复设计。
6. 检查当前功能与已有功能的接口关系。
7. 确认当前功能的详细设计范围。

功能设计必须与项目整体架构保持一致。

## 4.3 功能设计文档维护

每个功能必须独立维护一份功能设计文档。

功能设计文档应明确：

1. 功能模块划分。
2. 模块职责。
3. 输入和输出。
4. 数据结构。
5. 模块接口。
6. 模块依赖。
7. 业务流程。
8. 异常处理。
9. 测试方案。
10. 实施阶段和步骤。

设计过程中发现需要调整整体架构时，必须先进行架构影响分析。

确认调整后，先更新项目架构设计文档，再进入代码实施。

## 4.4 后续功能设计概要

确定当前功能详细设计时，必须根据项目整体架构规划后续功能。

在当前功能设计文档中记录后续相关功能的设计概要。

主要记录：

- 后续功能的主要模块。
- 预计职责。
- 预计数据结构及接口衔接。
- 与当前功能的依赖关系。
- 可能影响当前功能的架构约束。

后续功能的详细设计必须在其正式实施前重新审计和确认。

## 4.5 功能设计完成后的文档更新

当前功能设计完成后，必须：

1. 检查功能设计的完整性。
2. 检查与项目整体架构的一致性。
3. 检查与已有功能设计是否重复。
4. 检查模块依赖是否合理。
5. 检查测试方案是否完整。
6. 更新项目架构设计文档。
7. 更新项目进度跟踪文档。

# 五、项目实施原则

## 5.1 功能分阶段实施原则

1. 每个功能必须划分为若干实施阶段。
2. 阶段划分必须依据功能设计文档。
3. 每个阶段必须具有明确的实施目标、实施范围和交付标准。
4. 阶段之间必须明确依赖关系。
5. 不得在前置阶段未完成的情况下擅自进入后续阶段。

## 5.2 阶段实施前的检查

每个阶段开始前，必须：

1. 检查项目进度跟踪文档。
2. 检查之前阶段的完成状态。
3. 检查之前阶段的 pytest 测试结果。
4. 检查之前阶段的审计结论。
5. 检查之前阶段的 GitHub 提交记录。
6. 检查当前阶段的功能设计及实施范围。
7. 确认当前阶段具备实施条件。

只有前置阶段满足完成条件，才允许开始当前阶段。

当前阶段开始前，必须更新项目进度跟踪文档。

## 5.3 阶段完成条件

一个阶段只有同时满足以下条件，才能标记为已完成：

1. 阶段目标全部实现。
2. 阶段内全部步骤完成。
3. 适用的 pytest 测试通过；纯文档步骤完成规定的文档验证。
4. 涉及已有功能时，必要的回归测试通过。
5. 实施后审计通过。
6. 相关文档更新完成。
7. 临时文件及不必要备份清理完成。
8. GitHub commit/push 成功。
9. 进度跟踪文档更新完成。
10. 没有未处理的重大阻塞问题。

存在已接受的非阻塞遗留事项时，必须明确记录其影响和处理计划。

## 5.4 步骤划分原则

1. 每个阶段必须划分为若干具体实施步骤。
2. 每个步骤必须具有明确的实施目标。
3. 每个步骤必须具有明确的实施范围。
4. 每个步骤必须能够独立验证。
5. 每个步骤必须具有明确的完成标准。
6. 步骤划分应保持合理粒度，避免过度拆分没有独立交付价值的工作。
7. 步骤之间必须明确前后依赖关系。

## 5.5 步骤实施前的检查

每个步骤开始前，必须：

1. 阅读项目进度跟踪文档。
2. 检查之前步骤是否已经完成。
3. 检查之前步骤的测试结果。
4. 检查之前步骤的审计结论。
5. 检查之前步骤的 GitHub 提交记录。
6. 阅读当前步骤对应的功能设计。
7. 检查当前步骤涉及的现有代码及相关模块。
8. 确认当前步骤的实施目标和边界。

只有前置步骤已经完成，才允许实施当前步骤。

步骤开始前，必须将当前步骤更新为进行中。

## 5.6 步骤标准实施流程

每个步骤必须严格遵循以下流程：

**第一步：实施前检查**

检查当前步骤的前置条件、相关代码、功能范围、设计方案及当前 Git 工作区状态。

**第二步：实施**

按照已确认的方案执行代码开发或文档维护，不得擅自扩大实施范围。

**第三步：测试及验证**

根据当前步骤实际修改内容执行验证：

1. 涉及代码、测试逻辑、运行行为、配置或可执行接口契约的步骤，执行对应 pytest 测试，以及必要的回归测试和集成测试。
2. 纯文档维护步骤，如果不影响代码、运行行为、配置或测试逻辑，不强制执行无关的 pytest 测试。
3. 纯文档维护步骤必须执行内容、结构、引用、编码、差异及完整性检查。
4. 文档修改实际影响代码运行、配置、接口契约或测试逻辑时，必须补充相应的 pytest 验证。

记录实际执行的验证命令、测试数量、通过数量、失败情况及不适用 pytest 的原因。

**第四步：实施后审计**

检查：

- 代码修改是否符合设计。
- 是否影响已有功能。
- 模块职责和依赖关系是否合理。
- 数据结构和接口是否正确。
- 适用的测试是否完整。
- 文档是否与实际实现一致。
- 是否存在不必要的代码或文件。
- 本次修改是否超出已确认的实施范围。

**第五步：清理**

清理本步骤产生且确认不再需要的临时文件、调试文件和备份文件。

不得清理未经确认的项目原始文件、正式文档或其他需要保留的数据。

`reports/` 目录及其历史报告、审计记录和备份文件必须遵循保留原则。未经用户明确批准，不得删除、覆盖、移动或修改其中的文件，也不得将与当前步骤无关的 `reports/` 文件纳入提交。

不创建 Qdrant 备份恢复机制。

**第六步：Roadmap 更新及提交前审计**

在提交当前步骤之前，先更新唯一项目进度跟踪文档。

记录当前步骤已经实际完成的实施内容、验证结果、审计结论、清理结果及尚未完成的 GitHub 交付状态。不得提前记录尚未发生的 Commit SHA 或推送结果。

随后执行提交前审计：

1. 检查 Git 工作区状态。
2. 检查完整的未暂存 Git diff。
3. 检查暂存文件清单。
4. 检查完整的 `git diff --cached`。
5. 确认暂存文件仅包含当前步骤相关交付内容。
6. 暂存操作必须使用明确指定的当前步骤交付文件路径。不得使用 `git add .`、`git add -A` 或其他无差别批量暂存方式。
7. 确认 `reports/` 中未经批准的文件没有进入暂存区。
8. 确认没有误提交临时文件、调试文件或不必要的备份文件。
9. 确认代码、测试和正式文档已经同步。

只有提交范围和完整 staged diff 审计通过，才允许执行提交。

**第七步：GitHub 提交及推送**

1. 对当前步骤执行独立 Git commit。
2. 记录该步骤交付 Commit SHA。
3. 执行 Git push。
4. 核实远端分支已包含该 Commit SHA。
5. 确认本地与远端版本关系正确。

不得将多个尚未验证的步骤合并为一次提交。

**第八步：补录最终交付状态**

GitHub 推送成功后，更新唯一项目进度跟踪文档，补录：

- 当前步骤的交付 Commit SHA。
- GitHub push 结果。
- 推送后的远端版本核验结果。
- 遗留问题。
- 下一步计划。

补录后的 Roadmap 变更必须再次执行完整差异及暂存范围审计，并通过独立的 Git commit/push 提交。

补录记录应引用当前步骤的交付 Commit SHA。Roadmap 不要求在自身内容中递归记录包含该补录内容的 Commit SHA；补录提交本身通过 Git 历史保持可追溯。

只有实施、适用验证、实施后审计、清理、交付提交、推送核验及最终进度记录全部完成，才允许将当前步骤标记为已完成。

## 5.7 测试失败及步骤阻塞处理

如果适用的 pytest 测试失败：

1. 不得将当前步骤标记为完成。
2. 不得进入依赖当前步骤的后续步骤。
3. 分析测试失败原因。
4. 修复实际问题。
5. 重新执行相关测试。
6. 重新进行必要的审计。
7. 更新进度跟踪文档。

纯文档维护步骤如果没有适用的 pytest 测试，则按照对应的文档验证结果判断是否通过，不得虚构 pytest 测试结果。

如果出现无法继续实施的问题，必须将步骤标记为阻塞，记录阻塞原因、影响范围和解决方案。

## 5.8 需求变更及架构调整管理

实施过程中发现原有功能范围、设计方案或架构需要调整时：

1. 暂停受影响的实施工作。
2. 分析调整原因。
3. 分析对现有功能和后续功能的影响。
4. 确认是否需要调整功能范围。
5. 确认是否需要调整项目架构。
6. 更新相关功能范围文档。
7. 更新相关功能设计文档。
8. 必要时更新项目功能清单及项目架构设计文档。
9. 更新项目进度跟踪文档。
10. 确认调整方案后再继续实施。

不得在未进行影响分析的情况下，直接改变既定实施目标。

# 六、项目质量、文档及版本管理补充原则

## 6.1 现有功能保护

1. 所有升级必须以保护现有正常功能为前提。
2. 修改公共模块前必须分析影响范围。
3. 修改公共接口前必须分析调用关系。
4. 修改数据结构前必须分析相关功能和数据的影响。
5. 删除模块、文件或功能前必须进行必要性评估。
6. 不得以牺牲已有功能的方式解决新功能问题。

## 6.2 文档与代码一致性

每次步骤实施完成后，必须检查：

1. 项目功能清单是否与实际功能规划一致。
2. 功能范围文档是否与实际交付一致。
3. 项目架构设计是否与实际代码一致。
4. 功能设计文档是否与实际实现一致。
5. 项目进度跟踪是否与实际实施状态一致。

如果实际实现与原设计不同，必须同步更新相关设计文档，并记录调整原因。

## 6.3 GitHub 版本管理

1. 所有正式代码、测试和项目文档统一进行 Git 版本管理。
2. 每个实施步骤完成后，必须进行独立的 GitHub commit/push。
3. 不得将多个尚未验证的步骤合并为一次提交。
4. 每次提交必须能够对应具体实施步骤。
5. 每次提交必须记录 commit SHA。
6. 每次提交前必须检查完整 Git diff、暂存文件清单及完整 staged diff。
7. 暂存内容必须严格限定为当前步骤相关交付文件，不得直接提交未经审计的整个工作区。暂存操作必须明确指定文件路径，禁止使用 `git add .`、`git add -A` 或其他无差别批量暂存方式。
8. `reports/` 中未经用户明确批准的文件不得删除、覆盖、移动或纳入提交。
9. 不得将无关文件、临时文件、调试文件或不必要备份文件提交到 GitHub。
10. 每个步骤必须先更新 Roadmap 中的实际实施及验证状态，再执行交付提交；push 成功后补录 Commit SHA 和远端核验结果。
11. 最终补录的 Roadmap 变更必须再次独立审计并提交、推送。

## 6.4 交付完成标准

项目功能、阶段和步骤均必须以实际交付结果作为完成依据。

完成标准统一为：

**实施完成 + 适用的 pytest 验证通过或纯文档验证通过 + 实施后审计通过 + 文档一致性检查通过 + 清理完成 + GitHub commit/push 成功 + 最终进度跟踪更新完成。**

任何一项未完成，均不得将对应工作标记为正式完成。

# 七、项目实施统一执行要求

今后所有劳动争议法律知识库项目工作，必须遵循以下统一执行顺序：

1. 阅读本项目开发与实施管理规范。
2. 阅读唯一项目功能清单文档。
3. 阅读唯一项目架构设计文档。
4. 阅读唯一项目进度跟踪文档。
5. 阅读当前功能范围文档。
6. 阅读当前功能设计文档。
7. 检查前置阶段和前置步骤的完成状态。
8. 确认当前实施目标、范围和完成标准。
9. 执行实施前审计。
10. 按照既定步骤开展工作。
11. 执行适用的 pytest 测试验证；纯文档步骤执行相应的文档验证。
12. 执行实施后审计。
13. 完成文档一致性检查及文件清理。
14. 按照第 5.6 节完成 Roadmap 提交前更新、提交前审计、GitHub commit/push 及远端版本核验。
15. 推送成功后补录 Commit SHA 和最终交付状态，并对补录后的 Roadmap 变更再次审计、独立 commit/push。

如果对话中断、项目工作暂停或重新开启，必须首先根据项目文档恢复真实实施状态。

不得仅根据历史对话内容推断项目已经完成的工作。

不得重复实施已经有充分完成证据的步骤。

不得跳过尚未完成的前置步骤。

不得擅自改变已确认的项目实施方案。

如果发现项目文档与实际代码状态不一致，必须先进行只读审计，确定真实状态，再决定如何修正。

# 八、最终管理原则

本规范是劳动争议法律知识库项目的最高层级开发与实施管理规范。

项目所有功能规划、架构设计、代码开发、测试验证、文档维护和版本交付均必须遵循本规范。

项目实施过程中，应始终坚持以下原则：

1. **整体规划优先**：先规划整个项目，再分功能实施。
2. **现状审计优先**：先审计现有功能，再确定优化方案。
3. **文档先行**：先确定功能范围和架构设计，再开展代码开发。
4. **架构统一**：所有功能必须服从项目整体架构。
5. **现有功能保护**：优化升级不得无故破坏已有功能。
6. **测试统一**：全部自动化测试使用 pytest。
7. **逐步交付**：每个功能分阶段，每个阶段分步骤。
8. **过程可追溯**：每个步骤均有实施、验证、审计和版本记录。
9. **文档唯一**：项目级功能清单、项目架构设计和项目进度跟踪文档均只维护唯一正式版本。
10. **状态真实**：所有完成状态必须有实际证据支持。
11. **版本可追溯**：每个步骤完成后必须提交 GitHub。
12. **数据来源可靠**：法律数据以权威原始法律文件为依据，Qdrant 数据问题通过重新入库解决，不建立专门的备份恢复机制。

**最终目标：建立一套功能边界明确、整体架构统一、实施过程规范、测试结果可靠、项目文档完整、代码版本可追溯的劳动争议法律知识库工程体系。**
